# Local GGUF Models for DeepSeek Harness

Run **GGUF models on your own machine** from DeepSeek Harness — through LM Studio,
or through a `llama-server` this plugin starts directly on a model file.

Beyond wiring up the model route, the plugin reads GGUF headers itself, probes your
CPU/RAM/VRAM, estimates the memory a configuration will actually use, and
recommends load parameters for *this* machine — the same job LM Studio's model
loader does, exposed to the Harness agent and the Web UI.

---

## What you get

| Surface | What it does |
|---|---|
| `lmstudio` provider route | Talks to LM Studio's OpenAI-compatible server on `127.0.0.1:1234`, starting LM Studio and its server on demand. |
| `local-gguf` provider route | Starts `llama-server` on one `.gguf` file — **LM Studio does not need to be running.** Uses the CUDA/Vulkan/CPU llama.cpp runtime LM Studio already downloaded. |
| **Settings → Models panel** | Choose a `.gguf` file; edit context length, GPU layers, threads, batch sizes, KV-cache type, flash attention and KV offload; watch a live VRAM/RAM memory bar with the reasoning behind the recommended values. **Add or remove model folders**, **download models**, and **save the current parameters as the route's defaults** — persisted through the Loader, so they survive a restart. |
| `local_models` tool | Lists every GGUF model found on this machine with architecture, quantization, size, and whether it fits in the detected VRAM. |
| `local_model_recommend` tool | Recommended GPU layers, context length, KV-cache type, batch sizes and thread count — plus the memory estimate, the reasoning, and the equivalent `llama-server` command line. |
| `local_backend` tool | Status / start / stop of LM Studio and the managed `llama-server` processes. |

### Where each thing lives

- **Choosing a model** — the composer's model selector, at the right of the message
  box. Local models appear under `LM Studio (local)` and `Local GGUF (direct
  llama.cpp)`. Model choice is **per conversation**, so one chat can use a local
  model while another uses a cloud one; nothing needs to be switched globally.
- **Configuring parameters** — Settings → Models. The DSH model picker is
  shell-owned and has no plugin seat, so configuration deliberately lives on the
  Models page rather than in the picker popup. The panel renders in the page
  **footer**, which is an unconditional slot, so it is reachable whether or not a
  provider row exists for these routes — and again inside the route's own provider
  card when one is shown.

### Language

The panel follows the application language through the Client locale service
(`ctx.locale`), shipping **English and Chinese** dictionaries and re-rendering on a
language switch. The recommendation's explanatory lines are generated by the Host,
so each one is emitted twice: as English prose for the agent tools, which read it
in a transcript, and as a machine key with its parameters (`rationaleNotes` /
`warningNotes`) that the panel renders in the active language. A key this client
build does not know falls back to the Host's prose, so a mismatch degrades to
English rather than to a raw key. Without the locale service the built-in
dictionary follows the browser's language.

## How it decides

The estimator models what a llama.cpp backend really spends:

```
total = weights + KV cache + compute buffer + runtime overhead
```

Each term comes from the model's **actual tensor table**, not from the file size:

- **Weights** — every tensor's element count is multiplied by its ggml type's true
  block size, split into per-transformer-block bytes and everything else. That split
  is what makes partial GPU offload arithmetic: offloading `L` of `N` blocks costs
  the first `L` block entries, so "how many layers fit" is a sum, not a ratio.
- **KV cache** — `n_layer × n_kv_heads × (head_dim_K × bytes_K + head_dim_V × bytes_V) × context`.
  Grouped-query attention and quantized caches are both handled, and models with
  sliding-window attention are charged the window instead of the full context on
  their windowed layers.
- **Compute buffer** — scales with the logical batch and vocabulary; halved when
  flash attention is on.
- **Overhead** — a live CUDA context costs a few hundred MiB before any weights load.

The recommendation then reserves ~8 % of VRAM for the desktop, offloads as many
layers as fit (keeping the KV cache on the GPU while it still fits), spends what is
left on context length, and falls back to a CPU configuration with thread and batch
sizes matched to the machine when a model cannot fit at all.

Every result is labelled an estimate. A managed backend is started with `-lv 4`
(trace), the level at which llama.cpp logs its real per-device allocations —
measured to add ~195 startup lines and only ~34 lines for a whole generation,
against ~8000 for full verbosity. Those lines are parsed into a **measured** figure
reported beside the estimate, so the prediction can be checked against reality:

| Term | Measured (llama.cpp) | Estimated | Error |
|---|---|---|---|
| KV cache | 1.75 GB | 1.75 GB | **0.0%** |
| Offloaded weights | 8.15 GB | 7.88 GB | 3.2% |
| **GPU total** | **9.99 GB** | **10.67 GB** | **6.8% (high)** |
| System RAM | 0.73 GB | 0.93 GB | 26.8% (0.2 GB absolute) |

The GPU estimate deliberately errs high: a recommendation that slightly
over-reserves VRAM still loads, while one that under-reserves fails.

## Install

The plugin is a Harness **bundle**. Point the installer at this directory — the
checkout path, wherever you cloned it:

```
plugin_manager  action: install_bundle  target: <path to this directory>
```

Or from the Web sidebar: **Plugins → Install → local path**, and pick the folder.

Installing links the directory into the active profile and adds the bundle to its
`dsh.profile.bundles`. Nothing is copied, so editing the checkout is editing the
installed plugin.

> **After changing plugin source, restart Harness.** The Loader caches an imported
> module by URL. A bundle linked from the workspace keeps the same URL across
> toggles, so edits to an already-activated plugin need a restart to take effect.
> Installing a bundle for the first time activates immediately. This is Harness
> behaviour, not a limitation of this plugin.

### Requirements

| | |
|---|---|
| Harness | `0.2.0-rc.2` (the plugin uses only the `llm`, `tools`, `settings`, `configEditor` and `webServer` services, and declares no `@deepseek-ai/*` dependency) |
| Node | any version Harness itself runs on; the plugin uses only `node:*` builtins and global `fetch` |
| LM Studio | optional — needed for the `lmstudio` route, for its downloaded llama.cpp runtimes (used by the `local-gguf` route), and for model downloads |

### Run the tests

```
node test/run.mjs
```

No Harness, no dependencies, no network. Real GGUF files are picked up
automatically when present and the real-model checks are skipped when they are not.

## Configuration

With **no configuration at all**, both routes register and work: the model
directories are discovered from LM Studio's own index, and load parameters come
from the recommendation engine. Everything below is optional, set on the plugin's
row in `cordis.patch.yml`:

```yaml
- id: local-gguf
  config:
    # Extra directories to scan for .gguf files (shared by both routes).
    modelDirs: ['D:\models']
    # Include the directories LM Studio has already indexed. Default: true.
    includeLmStudioDirs: true
    # Register the three agent tools. Default: true.
    tools: true
    # Fraction of VRAM held back for the desktop. Default: 0.08.
    vramReserveRatio: 0.08

    providers:
      lmstudio:
        displayName: 'LM Studio (local)'
        baseURL: 'http://127.0.0.1:1234/v1'   # /v1 is added if omitted
        autoStart: true                        # launch LM Studio + its server on demand
        apiKey: LMSTUDIO_API_KEY               # optional; a credential reference

      local-gguf:
        displayName: 'Local GGUF (direct llama.cpp)'
        backendId: auto                        # or an exact runtime id
        llamaServerPath: 'C:\path\to\llama-server.exe'
        llamaServerVendorDir: 'C:\path\to\cuda\vendor'   # prepended to PATH
        # Pin load parameters instead of using the recommendation:
        contextLength: 16384
        gpuLayers: 40
        port: 8080
```

### Load parameters the recommender decides

| Parameter | `llama-server` flag | Notes |
|---|---|---|
| Context length | `-c` | Capped at the model's native context; grown while VRAM allows. |
| GPU layers | `-ngl` | Largest block count that fits the VRAM budget. |
| CPU threads | `-t` | Physical core count (estimated as logical ÷ 2 on SMT x86). |
| Eval batch size | `-b` | 2048 on GPU, 1024 on CPU. |
| Physical batch size | `-ub` | 512 on GPU, 256 on CPU. |
| Flash attention | `-fa` | On for GPU execution. |
| K/V cache type | `-ctk` / `-ctv` | `f16`, or `q8_0` when VRAM is tight. |
| KV offload | `--no-kv-offload` | Emitted only when the cache stays in RAM. |
| MoE weight placement | `--n-cpu-moe` | Recommended for MoE models under partial offload. |
| Log verbosity | `-lv 4` | Trace level, required for llama.cpp's own allocation lines. Disable with `verboseLogs: false`. |

## Choosing a model in Harness

After installation the composer's model picker lists models under **LM Studio
(local)** and **Local GGUF (direct llama.cpp)**. Selecting one and sending a message
starts whatever is needed — the LM Studio server, or a managed `llama-server` on
that exact file — and streams the reply with tool-call support.

The `lmstudio` route addresses models the way LM Studio does
(`publisher/repository/file.gguf`); the `local-gguf` route addresses the file path.
Both ids also work when no server is running yet, so the picker stays useful
before anything is started.

## Verification

`node test/run.mjs` — **203 assertions, 0 failures**, no Harness required.

The numbers below come from one reference machine: Intel i9-13900HX, 32 GB RAM,
**RTX 5070 Ti Laptop 12 GB**, LM Studio with its CUDA llama.cpp runtimes, and a
model folder outside the LM Studio default. Paths are shortened to `<models>`.

**Live end-to-end inference** — the plugin started a real `llama-server` on a real
model with its own recommended arguments and streamed real completions:

```
llama-server.exe --model <models>\...\Llama-3.1-SuperNova-Lite-14B.Q5_K_M.gguf
  --alias Llama-3.1-SuperNova-Lite-14B.Q5_K_M --host 127.0.0.1 --port 8080
  -c 8192 -ngl 55 -t 16 -b 2048 -ub 512 -fa on --jinja
```

- Streamed 62 chunks for one completion in 3.8 s; usage reported 41 in / 59 out /
  100 total tokens. `usage` precedes `finish`, nothing follows it, and every opened
  block is closed — checked as explicit invariants.
- **Full agent loop verified** on `gpt-oss-20b`: the model emitted a `reasoning`
  block, then a real `tool-call` block (`read` with `{"file_path":"config.yaml"}`),
  `finish` reason `tool-calls`; feeding the tool result back produced the correct
  answer (`8080`). All seven invariants passed.

**GGUF reader** — all four real chat models parse in 0.05–0.10 s each, with exact
metadata:

| Model | arch | quant | layers | native ctx | KV heads | weights |
|---|---|---|---|---|---|---|
| Qwen3.8-27B | `qwen35` | Q6_K | 65 | 262144 | 24 / 4 | 20.88 GB |
| gpt-oss-20b | `gpt-oss` | MXFP4 | 24 | 131072 | 64 / 8, 32 experts | 11.27 GB |
| Qwen3-VL-32B | `qwen3vl` | Q4_K | 64 | 262144 | 64 / 8 | 18.40 GB |
| Llama-3.1-SuperNova-Lite-14B | `llama` | Q5_K | 56 | 131072 | 32 / 8 | 8.78 GB |

Per-layer byte accounting is checked to sum exactly to the tensor table, and
`mmproj` projectors and embedding models are classified apart from chat models.

**Hardware probe** — VRAM read as **11.91 GB** for the RTX 5070 Ti Laptop, matching
`nvidia-smi` (12227 MiB = 11.94 GiB). Two traps the probe corrects: LM Studio's
Vulkan survey reports shared memory as "total" (27.5 GB for this 12 GB card), and
integrated adapters report system RAM as their dedicated memory.

**Recommendations** — realistic and machine-specific:

| Model | Recommendation | Estimate |
|---|---|---|
| Llama-3.1-14B Q5_K | 55/56 layers, ctx 8192, f16 KV | GPU 10.68 GB, RAM 0.94 GB |
| gpt-oss-20b MXFP4 | 22/24 layers, ctx 16384, f16 KV | GPU 10.96 GB, RAM 2.02 GB |
| Qwen3.8-27B Q8_0 | 32/65 layers, ctx 8192, f16 KV | GPU 10.88 GB, RAM 12.16 GB |

Every recommendation is asserted to stay inside the detected VRAM budget.

**Wire protocol** — 14 unit assertions over recorded SSE streams: plain text,
reasoning + text interleaving, tool calls split across deltas with no id on the
continuation, parallel tool calls, `length` → `max-tokens`, empty-stream failure,
malformed tool JSON repair, and message/tool translation.

**Tool output** — every tool result is validated against a faithful replica of the
runtime's own lossless-JSON validator (`isJsonNumber` rejecting `-0`, plain-record
and dense-array predicates), itself proven non-vacuous by rejecting `undefined`
properties, `-0`, `NaN`, sparse arrays, class instances and functions.

**Web routes and Client module** — every read endpoint answers correctly
(200/400/404/405), `/inspect` honours every override it is sent, and the write
endpoints reject a malformed action with 400 rather than surfacing an internal
failure. The client half registers exactly two cells under the right ids, renders a
real tree in the footer — including the model-folder and download controls —
returns `null` for a provider card it does not own, and throws nothing.

**Configuration writes** — model folders are added, de-duplicated
case-insensitively and removed; pinned parameters merge per route, clear on `null`,
and drop the emptied provider block; sibling configuration and hand-written
provider blocks survive every write; a missing configuration editor is reported by
name rather than failing obscurely.

**Localization** — both dictionaries are registered and cover an identical key set;
every `t('…')` key used anywhere in the client exists in both, so a literal can
never render as a raw key; the panel renders Chinese chrome under a `zh` locale and
English under `en`, with no English leaking into the Chinese tree; placeholders
substitute; and an unregistered language still renders real text rather than keys.
On the Host side, every line `recommendConfig` can emit is asserted to carry a key,
and all fifteen keys are asserted to have both translations — closing the loop
between the Host's prose and the panel's rendering.

**Backend view consistency** — `list()` and `describe()` are asserted to produce
byte-identical `measured` objects, after a real defect where `list()` returned the
raw per-device accumulator and `describe()` the summarized one. The same running
backend therefore read as measured numbers through `start` and as "unavailable"
through `status`.

**llama-server log parsing and estimator accuracy** — the suite embeds the verbatim
startup log of a real llama.cpp 0.6.0-dev run and asserts the parser recovers every
per-device buffer, keeps the real allocation rather than the sizing pass's zeros,
ignores the `output buffer size` line that would otherwise be mistaken for a KV
buffer, and handles the older single-total reporting style. It then closes the loop
with the table above as assertions.

**Not verified:** the panel's *visual* rendering. A plugin whose source changes
after activation keeps its cached module until Harness restarts, so the settings
panel has been verified only down to the render tree, not in a browser.

## Known limitations

- **Text-only.** Both routes advertise `inputModalities: ['text']`, so Harness sends
  image placeholders rather than image bytes. Vision models such as Qwen3-VL can be
  loaded and their `mmproj` projector is passed to `llama-server`, but images are
  not forwarded from the conversation yet.
- **`lms load` cannot set most parameters.** LM Studio's CLI exposes only
  `--context-length` and a `--gpu` memory ratio. The plugin uses the HTTP
  `POST /api/v1/models/load` endpoint (LM Studio 0.4.0+) when available, which
  accepts context length, eval batch size, flash attention, expert count and KV
  offload; it falls back to the CLI and reports which parameters were not applied.
- **Estimates, not measurements.** The compute-buffer term is calibrated, not
  derived, and is the least precise part of the estimate. llama.cpp's own reported
  figures are shown alongside it once a backend is running.
- **No Config schema.** A bundle linked from outside the Harness installation
  cannot resolve `@deepseek-ai/*` specifiers, so the plugin declares no
  schemastery `Config` and validates its own configuration defensively instead.
  Configuration therefore has no generated form on the Plugins page; use the
  Models-page panel, which writes through `configEditor`, or edit
  `cordis.patch.yml` as shown above.
- **Downloads need LM Studio running.** The panel's Download action is a thin,
  honest passthrough to `lms get`, which talks to the LM Studio daemon. With LM
  Studio closed it reports that, rather than failing silently. Adding a folder of
  models you already have never needs LM Studio.
- **Partial offload is slow.** Splitting layers across PCIe costs throughput; the
  plugin says so in its warnings rather than hiding it.

## Layout

This directory is the whole project — there is no build step, no `node_modules`,
and nothing is generated. Every file is source.

```
package.json          bundle manifest: the `dsh.bundle` patch and the `dsh.client` half
cordis.patch.yml      the one Loader row this bundle inserts
index.js              plugin entry: registers routes, discovery, tools and web endpoints
client.js             Client half: the Models-page load-configuration panel
lib/gguf.js           dependency-free GGUF header/metadata/tensor reader
lib/hardware.js       CPU, RAM and VRAM probe with ordered fallbacks
lib/estimate.js       memory model and the recommendation engine
lib/models.js         model directory scan + header cache
lib/lmstudio.js       LM Studio discovery, REST API and CLI control
lib/backend.js        managed llama-server processes
lib/adapter.js        the Harness LLM adapter
lib/openai-wire.js    OpenAI <-> Harness message and stream translation
lib/runtime.js        route resolution, catalog, backend lifecycle
lib/tools.js          the three agent tools
lib/web-routes.js     endpoints feeding the Client panel: reads and write actions
lib/config-writer.js  persists model folders and pinned parameters via configEditor
lib/dsh-compat.js     the small slice of runtime shape this plugin needs
locale/{en,zh}.json   the bundle's title and description on the Plugins page
icon.svg              bundle icon
test/                 offline suite: 203 assertions, no Harness required
LICENSE               MIT
```

The panel's own UI strings live in `client.js` next to the components that use
them, and are registered with the Client locale service at activation.
